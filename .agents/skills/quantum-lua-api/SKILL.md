# Lua API reference

`quantum-reflector` reads the LuaBridge chains in `engine/core/script/binding` and the
C++ headers they name, builds the manifest `reflect` uses (`buildManifest`,
`tools/reflector/generate.cpp:516`), then renders it twice: `docs` writes the Markdown
reference (`renderLuaDocsMarkdown`, `generate.cpp:1058`) and `types` writes the Lua
definition file (`renderLuaTypesFile`, `generate.cpp:1164`) that the editor embeds and
drops into every project as `Types.lua`. Nothing in the engine consumes the Markdown -
it exists for humans, agent context and reference tables - so its risk is silent
staleness, not a broken build. The types output *is* consumed: it is compiled into the
editor, so a stale or empty `lua_types.h` fails the editor build loudly instead of
quietly.

## Commands

Build once, then run the tool directly:

```bash
cmake --build "$QUANTUM_BUILD_DIR" --target quantum-reflector --config Debug
"$QUANTUM_BUILD_DIR/Debug/quantum-reflector.exe" docs \
  --bindings engine/core/script/binding --engine-core engine/core \
  --out "$QUANTUM_BUILD_DIR/generated/lua_api.md"
"$QUANTUM_BUILD_DIR/Debug/quantum-reflector.exe" types \
  --bindings engine/core/script/binding --engine-core engine/core \
  --usage tools/reflector/lua_usage.lua \
  --out "$QUANTUM_BUILD_DIR/generated/Types.lua"        # or lua_types.h for the header
```

`--bindings` is required; `--engine-core` defaults to `<bindings>/../..`; `--out` is
required. `types` picks the form from the `--out` extension: `.h`/`.hpp` wraps the file
as `quantum::editor::getLuaTypesFileChunks()` / `getLuaTypesFileText()`
(`renderLuaTypesHeader`, `generate.cpp:1400`), anything else writes plain Lua. The CLI
is `tools/reflector/reflector_main.cpp` - `printUsage` `:24-~60`, `catalog` `:225-232`,
`docs` `:233-240`, `types` `:241-261`, `reflect` `:263-276`, `check` after that
(usage/requirement checks `:124-142`). Exit codes: 0 success (or `check` found no
drift), 1 `check` found a difference, 2 usage error, 3 I/O error. Success prints
`[quantum-reflector] Generated Lua API docs <path>` / `Generated Lua types header|file
<path>` followed by an indented `Classes: N, Methods: N, ...` line (`printSummary`).

`check` does **not** read `lua_api.md` or `Types.lua`: it re-reads the C++ header named
by `--against` and reports whether regeneration would change that header. To prove a
Lua output is current, regenerate and diff (see the last section).

## CMake targets

- `generate_lua_docs` (`CMakeLists.txt:591-605`) is opt-in and deliberately **not** in
  any `add_dependencies`, so a normal editor build never regenerates the Markdown. Run
  it (or the tool) after any binding or header change.
- `generate_lua_types` (`:610-625`) renders `lua_types.h` with `--usage
  ${CMAKE_SOURCE_DIR}/tools/reflector/lua_usage.lua` and **is** a build dependency of
  both editor targets (`configure_quantum_editor_target`, `:802-805`, used at `:893` and
  `:1017`). `${GENERATED_DIR}` is already an editor include directory, so
  `editor/Project.cpp` just `#include "lua_types.h"`. Consequences: editing
  `lua_usage.lua` or any binding recompiles `Project.cpp`, and a reflector that fails
  to generate stops the editor build.

## Output format

`build/generated/lua_api.md` lives in the build tree; never hand-edit or commit it.

- `:1` is the banner `<!-- Auto-generated by quantum-reflector docs - DO NOT EDIT -->`,
  `:2` the title `# Quantum Lua API`, `:4` a one-line description of the bindings root.
- `## Contents` (`:6`) then `**Classes**` (`:8`) with one `[Name](#name)` anchor link
  per class (`:10-49`), in binding registration order.
- One `## <Class>` per class (`## Action` `:51`): ``Base: `EntityHandle` `` when the
  binding derives (`:53`), then `### Constructors` (`- `Action(Scene)``), `### Methods`
  (`- `Action:setTarget(Object target)``, or `- `Action:isRunning() -> bool`` when the
  return type is known), and `### Properties` (``- `ownedTarget` - `bool` ``).
- `## Engine` (`:396`) instead carries `### Static methods` (`:398`, bare names with no
  `Class:` prefix), `### Events` (`:428`) and `### Constants` (`:460`), also bare.
- `## Enums` (`:3979`) then one `### <Enum>` per enum with its members.

Rows are plain bullets, not tables, so the file diffs cleanly.

## Types.lua output

`build/generated/Types.lua` (plain) and `build/generated/lua_types.h` (embedded) hold
the same text: 6591 lines, one block per class in binding order, then enums, then the
globals, then the hand-written usage chapter. Never hand-edit either - `lua_types.h` is
regenerated by the build and the usage chapter lives in `tools/reflector/lua_usage.lua`.

- `---@diagnostic disable` + `---@meta` at the top, so LuaLS treats it as a definition
  file and a person can open it as documentation.
- Per class: `---@class Scene: EntityRegistry` (the base is emitted only when the
  binding registers the class with `deriveClass`), `---@overload` rows for
  constructors, `---@field name type` for properties (suffixed `(read-only)` when no
  setter is bound), events (`(event)`, typed `function`) and constants (`(constant)`),
  then `ClassName = {}` and one real `function ClassName:method(params) end` /
  `ClassName.static(params) end` per method, each preceded by `---@param` / `---@return`.
- Enums: `---@enum Name` + `Name = { MEMBER = 0, ... }`. Names bound as a class too
  (e.g. an enum namespace sharing a class name) extend the existing table with
  `Name.MEMBER = k` rows instead of redeclaring it.
- Enum members and constants carry **positional placeholder numbers** - the reflector
  sees the names a binding registers, not the engine's values. Compare by name, never
  by number, and the file says so in its header.
- Globals the bindings put on the Lua global namespace (`getGlobalNamespace(L)
  .addVariable("NULL_ENTITY", ...)`) render last as `---@type T` + `NAME = ...`
  (`...` is the main-chunk vararg: "this exists" without inventing a value).
- Non-identifier bound names (the easing properties are literally `function`) become
  `-- property X: read it as obj["X"]` comments rather than invalid declarations.
- The usage chapter (`tools/reflector/lua_usage.lua`, ~1000 lines of numbered sections:
  script shape, `init`-only dispatch, events, input, bodies, picking, spawning, models,
  UI, audio, files, plus a "gotchas" list) is appended verbatim. It is the only part
  that is not derived from the manifest, so **it can drift from the API on its own** -
  every name in it was checked against the generated declarations, and any new claim
  must be proven against a binding file, not remembered.

`Project::writeLuaTypesFileToProject()` (`editor/Project.cpp:4741`) writes the embedded
text to `.quantum/engine-api/Types.lua`, called first inside
`copyEngineApiToProject()` (`:4664`, from `:4668`; that syncs the C++ headers and runs on
project open at `:5099` and `:5513`) via the idempotent `FileUtils::writeFile`. Inside
`.quantum` on purpose: the code editor's project-symbol scan skips dot-directories
(`editor/window/CodeEditor.cpp:466-471`) and the packer never sees it, so no script can
`require("Types")` and a shipped game does not carry 200 KB of comments. In-editor Lua
completion comes from `engine_api_suggestions.h`
(`CustomTextEditor::addEngineAPISuggestions`), not from this file.

Template projects commit their `.quantum/engine-api/` snapshot (2879 tracked files), so
opening one with an editor that has this feature leaves an untracked
`Types.lua` there like any other regenerated file - that is the repo's existing
convention, not a leak, and `.gitignore` deliberately does not exclude `.quantum`.

## How it is built

- Order is binding order: `classOrder` / `enumOrder` (`ApiIndex`, `generate.cpp:217`,
  filled at `:242`, `:259`, `:275`) follow the order the parser walks the binding files,
  so both documents track `registerClasses` (`LuaBinding.cpp:480`), not alphabetical
  order.
- Methods are indexed by `parent + '\x1f' + lowerAscii(name)` (`indexMethod`,
  `generate.cpp:231-233`) and looked up the same way (`:290-291`), so a getter can be
  matched to the property that owns it. `lowerAscii` `:208`, `propertyType` `:303`,
  unresolved types fall back to `"unknown"` (`:344`).
- A `Base:` line is emitted only when the binding's `Class` symbol contains `" : "`
  (`:243`); the base name is the text after it.
- Property types: `propertyType` (`:303`) prefers the accessor the binding actually
  names (`addProperty("shape", &Particles::getPositionInitializerShape, ...)` -> that
  method's return type), then falls back to `get` + CamelCase (`:320`), then to parsing
  the name. So a Lua property whose C++ getter has an unrelated name only types
  correctly because `reAddPropertyGetter` captured it.
- The binding regexes accept **one level of nested template angles**, because a bound
  name can itself be a template: `.beginClass<FunctionSubscribe<void()>>("X")` and
  `.deriveClass<T, FunctionSubscribe<void()>>("X")`. Before that, anything registered
  through such a base was invisible - `Ease` (33 statics, `ActionClassesLua.cpp:280-316`)
  was the casualty, and the Python generator that produced the old
  `engine_api_suggestions.h` shared the blind spot, so nothing in the tree listed those.
- Classes registered on the `FunctionSubscribe_` bases are skipped whole
  (`isSubscriptionBase`, `tools/reflector/parse_bindings.cpp:124`): they are real Lua
  names but internal, and ~30 unreadable class blocks would bury the API.
- An accessor is an **event** only when its binding assigns the state into it
  (`bindsLuaEvent`, `parse_bindings.cpp:115`, used at `:297` for `addStaticProperty`
  and `:318` for `addProperty`): the setter takes a `lua_State*` and its body ends in
  `... = L;`, which is how a `FunctionSubscribe` field is written from Lua. An
  enum-table constant also reads `lua_State`, so the assignment is what separates the
  two. Both rules changed the classification, so the counts moved together:
  `addProperty` used to be *always* a Property (+48 rows became Events) and
  `addStaticProperty` used to be an Event whenever the line merely contained `[]` or
  `lua_State` (-173 rows fell back to Constant, which is also why Constants read 232
  where the old baseline said 57). When a reclassification looks wrong, read the
  binding line itself - the predicate is a string match, not a type check.
- A non-event property/constant now carries the accessor it was bound through:
  `reAddPropertyGetter` / `reAddStaticPropertyGetter` capture `&Class::getThing`, and
  `reStaticPropertyLambdaType` captures a `[] () -> T` return type. Renderers use those
  to type a Lua name that is not literally `get<Name>`.
- Constants are found per class *and* on the global namespace
  (`reGlobalVariable` `:46`, scanned at `:177-181`); the latter get an empty `parent`,
  which is why `ApiIndex` (`generate.cpp:217`) never lets them into `classOrder` and the
  renderer can emit a separate globals block.

## Known gaps

- `cpp_only` methods (`generate.cpp:613`, JSON `:736` and `:765`) are real C++ methods that
  are not Lua-callable. They are counted in `CppMethods` but deliberately omitted from
  the Markdown; `SceneManager`'s public statics are the main case.
- Methods taking `std::function<...>` parameters (e.g. `Scene::registerScene`) are not
  matched to a manifest symbol.
- Inline `operator==` / `operator!=` definitions in headers are not matched.
- Unresolved types render as `unknown`; around 40 such symbols are accepted today.
- The header scanner is token-based with a text fallback
  (`tools/reflector/parse_headers.cpp:207-228`, fallback around `:341`). Unusual
  multi-line signatures can still be missed. Do not rewrite the scanner for one case -
  add the missing shape to the token path.
- **Inheritance is not flattened.** `deriveClass<Scene, EntityRegistry>("Scene")` yields
  `---@class Scene: EntityRegistry` (so LuaLS resolves `scene:findEntity(...)`), but the
  method rows themselves are listed once, under the class the binding block names
  (`EntityRegistry:findEntity`, `Types.lua:861`). The Markdown reference is the same: a
  `Base:` line and no re-listed inherited members.
- Overloads collapse: `parse_bindings` emits one Method per `addFunction` and ignores
  the `luabridge::overload<...>` argument lists (544 of them in the bindings), so the
  renderer keeps the first signature and its `-- also:` branch never fires. Capturing
  the rest needs a `Symbol::overloads` field, not a renderer tweak.
- Enum/constant numbers in `Types.lua` are placeholders (see above); the usage chapter
  is the only hand-written part and can drift on its own.

## Verification discipline

There are no unit tests. Prove a change with a byte comparison against a known-good
snapshot:

```powershell
cmake --build C:\quantum2\build --target generate_lua_docs --config Debug
$lines = Get-Content C:\quantum2\build\generated\lua_api.md
"$($lines.Count) lines"
Compare-Object -ReferenceObject (Get-Content $ref) -DifferenceObject $lines
```

Expected baseline for this tree (after the nested-template, event and global-variable
parser fixes and the `FogComponent` bindings): 4602 lines and Classes 156, Methods 939,
CppMethods 1264, StaticMethods 285, Properties 861, Constants 233, Events 105, Enums 67,
EnumMembers 332. An empty
`Compare-Object` result means identical. Any diff must be explained by the binding or
header edit you made - a changed property row or a lost class means the parser
regressed.

For the embedded form, prove the round trip instead of trusting the generator: unpack
`lua_types.h` back to bytes (each Lua line is one C++ literal, bytes >= 0x80 as `\ooo`,
so decode to a `bytearray`, never to `str` code points) and compare against the plain
`--out Types.lua` render, then `luac -p` the result. Verified good here: 6768 literals =
210652 bytes = byte-identical to the direct render, `luac -p` exit 0.

The rendered paths are normalised, so the output does not depend on how the tool was
invoked: `displayPath` (`tools/reflector/generate.cpp:23`) cuts every printed directory
at the checkout's own `engine/`, and the Types banner (`:1185`) plus the JSON
`bindings_dir` / `engine_core_dir` (`:716-717`) go through it. Absolute-from-the-root,
relative-from-the-root and absolute-from-another-CWD therefore render byte-identical
files - proven with `fc /b`. This matters because the editor writes Types.lua *into a
project*, and an earlier build baked `C:/quantum2/...` into line 5 of
`.quantum/engine-api/Types.lua` in five templates; those copies stay stale until each
project is reopened.

Neither document proves a **call shape**: they render C++ signatures, so an overloaded
setter or a `Base:`-inherited method reads as valid and LuaBridge rejects it at runtime.
For that, run the calls. `engine/components/checks/api_probe.lua` is the model - it issues
116 calls against the real bindings inside `quantum-engine`, and deliberately includes
"traps" that must be *rejected*; the runner prints
`[api] 116 calls probed against the real bindings, 0 failures, 0 traps now valid`, and a
trap flipping to `ok` means the binding gained the shape and the docs are behind.
`checks/kit_check.lua` is the other half: it loads every component the way
`initializeLuaScripts` does, so a property type the parser rejects shows up as a failure
before a scene ever touches it. Both need a fixture project with `assets/shaders/*.sdat`
(`quantum-build-verify`).
